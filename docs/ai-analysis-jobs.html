Жизненный цикл AI-анализа раунда

Как закрытие раунда превращается в строку очереди, кто её забирает, чем удерживает и что происходит, когда исполнитель засыпает посередине. Всё ниже прочитано из кода на ветке claude/free-ai-service-deploy-yk4tjj, а не из документации.

Основной путь

Пять участников. У Python-половины нет доступа к базе: данные она получает по MCP, состояние джобы меняет только через HTTP-эндпоинты Core.

Порядок сверки на шаге 21 не случаен. Личность проверяется до валидации содержимого — иначе callback, промахнувшийся раундом, мог бы пометить чужой здоровый run как проваленный.

Три ветки, ради которых очередь и существует

Каждая из них — это момент, когда исполнителя не стало, а раунд остался.

409 stale

Аренда потеряна: инстанс уснул, работу забрал другой

Состояния строки

В базе всего четыре состояния. Повторная попытка — это не отдельный статус, а тот же running с истёкшей арендой, который снова стал пригоден к захвату.

stateDiagram-v2
    [*] --> queued: закрытие раунда или ручной перезапуск
    queued --> running: claim · attempt+1 · lease 90 с
    running --> running: heartbeat каждые 30 с
    running --> running: аренда истекла и attempt меньше 3 — повторный claim
    running --> succeeded: callback прошёл сверку и валидацию
    running --> failed: fail, отказ валидации или lease_exhausted
    succeeded --> [*]
    failed --> [*]

Гашение просроченных — часть захвата, а не отдельный сборщик. Каждый claim сначала помечает lease_exhausted всё, что исчерпало попытки, и только потом ищет себе работу. Отдельного крона в системе нет.

Что на диаграммах отсутствует намеренно

POST /api/v1/webhook/events — живой эндпоинт на Python-стороне, который запускает тот же анализ без run_id и lease_token, а Core принимает такой callback как legacy. Core этим путём анализ не запускает: в исходниках нет ни одного отправителя round_closed вне тестов. Это остаток, а не механизм — поэтому его нет ни в одной последовательности выше.
